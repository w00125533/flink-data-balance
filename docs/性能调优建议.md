# 性能调优建议

本文档记录 Flink Benchmark 压测时关于 CPU、Slot、并行度、算子链、反压和延迟探针的调优原则。目标是让不同 Sink、不同小区规模的压测结果可复现、可比较。

## 1. CPU、Slot、并行度的关系

三个概念不要混用：

| 概念 | 含义 | 是否等价于 CPU |
| --- | --- | --- |
| CPU cores | 真实计算资源，决定 TaskManager 能拿到多少计算能力 | 是 |
| Task slot | Flink 调度资源槽，用于放置 subtask | 否 |
| Parallelism | 算子被拆成多少个并行 subtask | 否 |

推荐的 Benchmark 基线：

```text
CPU cores = N
TaskManager slots = N
主链路 parallelism = N
```

例如固定 6 核压测时：

```text
CPU cores = 6
TaskManager slots = 6
主并行度 = 6
source / enrichment / kpi / sink 默认 p6
低流量 cfg 可以 p1 或 p2
```

这不是说 1 个 slot 等于 1 个 CPU 核，而是为了让资源模型稳定，减少压测结果中的随机因素。

## 2. Slot Sharing Group 的 Slot 需求

默认情况下，同一个 Flink Job 里的大多数算子会在同一个 slot sharing group 中。此时一个 group 的 slot 需求通常取该 group 内最大的并行度，而不是把所有算子的并行度相加。

同一个 group：

```text
source p6 + enrichment p6 + kpi p6 + sink p4
slot 需求约为 max(6, 6, 6, 4) = 6
```

拆成两个 group：

```text
main group: source / enrichment / kpi p6
sink group: sink p4
slot 需求约为 6 + 4 = 10
```

所以拆 slot sharing group 不是省资源，而是做资源隔离。它能帮助定位 sink 是否拖慢上游，但代价是需要更多 slots，也会改变压测口径。

## 3. 一个 Slot 内多个算子的 CPU 调度

Slot 不是 CPU 调度器。一个 slot 内如果有多个算子，CPU 使用取决于算子是否被 chain。

如果算子被 chain：

```text
source -> map -> enrichment-metrics
```

这些算子通常在同一个 task thread 内顺序执行。一条记录会依次经过 chain 内的函数。此时 chain 内算子不是并行抢 CPU，而是共用同一条执行线程。

如果算子没有 chain，但共享同一个 slot：

```text
source-subtask-1
kpi-subtask-1
sink-subtask-1
```

它们通常是不同 task thread，在同一个 TaskManager JVM 内竞争 CPU，最终由操作系统调度。Flink 不会固定分配 source 30%、kpi 40%、sink 30% 这样的 CPU 比例。

## 4. Benchmark 推荐模式

常规压测模式：

```text
固定 CPU cores
slots = CPU cores
主并行度 = slots
不拆 slot sharing group
默认保持算子 chain
一次只跑一个 Benchmark job
```

诊断模式：

```text
固定 CPU cores
slots = CPU cores
只拆 chain，不拆 slot sharing group
用于观察 enrichment / kpi / sink 等关键节点的 busy、反压和吞吐
```

隔离模式：

```text
拆 slot sharing group
为 main / sink 等 group 分别配置 slot
只在需要强隔离定位时使用
```

隔离模式会改变资源消耗，不建议作为默认性能上限口径。

## 5. 多任务并发压测原则

性能压测最好一次只跑一个 Flink Job。多个 Job 同时运行时，不同 Job 之间不能共享同一批 slot，slot 需求需要按 Job 相加。

示例：

```text
集群总 slots = 12
Job A 需求 6 slots
Job B 需求 6 slots
可以同时运行
```

```text
集群总 slots = 12
Job A 需求 8 slots
Job B 需求 8 slots
总需求 16 slots，不够
```

并发压测会相互争抢 CPU、网络、Kafka、StarRocks、HDFS、Hive Metastore 等资源，不适合作为单个 Sink 的上限判断。

## 6. 反压和资源瓶颈判断

建议按以下顺序判断：

| 现象 | 判断 | 优先措施 |
| --- | --- | --- |
| CPU 总负载 > 85%，多个算子 busy 高 | 计算资源不足 | 增加 CPU 或优化热点算子逻辑 |
| 某算子 busy > 85%，下游无明显反压 | 该算子可能是 CPU 瓶颈 | 提高该算子并行度或优化逻辑 |
| 某算子反压高，但自身 busy 不高 | 瓶颈通常在下游 | 检查下游算子、sink、存储 |
| sink busy 不高但写入慢 | 外部存储或 connector 可能是瓶颈 | 看 connector write/commit、存储状态和 checkpoint |
| source backlog 增长 | Flink 消费跟不上生成速度 | 降低输入、加资源或定位下游反压 |
| checkpoint 耗时高 | 状态、sink commit 或存储元数据压力 | 增大 checkpoint 间隔、减少状态、检查存储 |

不要只看到反压就盲目提高当前算子的并行度。反压是下游压力向上游传播的信号，真正瓶颈经常在更下游。

## 7. 延迟探针和事件时间戳

事件中的 `eventTs` / `sourceEventTsAvg` 是延迟计算的时间基准。探针不负责生成新的业务时间戳，只负责读取这些字段，并用当前处理时间计算观测延迟：

```text
latency = currentProcessingTime - eventTs/sourceEventTsAvg
```

当前原则：

| 数据阶段 | 时间基准 |
| --- | --- |
| 原始 CHR / PM / CFG | 原始 `eventTs` |
| 1 分钟 CHR / PM 汇聚 | `sourceEventTsAvg/sourceEventTsMin/sourceEventTsMax` |
| KPI 1m / KPI 5m | 上游 CHR/PM 的 `sourceEventTs*` 加权合并 |
| 异常事件 | 触发异常的 KPI 或 CHR 的 `sourceEventTs*` |
| Sink 前探针 | Sink 输入记录中的 `sourceEventTsAvg` |

因此探针和事件时间戳不是直接冗余。事件时间戳是原始依据，探针输出的是采样后的 P50/P95/P99、吞吐和错误统计。报告使用探针指标，是为了避免事后扫描所有明细数据。

为降低观测开销，压测时建议使用采样：

```text
FDB_METRICS_SAMPLE_EVERY_RECORDS=N
FDB_SINK_METRICS_SAMPLE_EVERY_RECORDS=N
```

高压场景可以把 N 调大，例如 100 或 1000。采样会降低探针开销，但分位值会变成采样估计。

## 8. 固定 CPU 压测建议

本地 Docker 环境建议增加硬约束：

```text
TaskManager CPU cores = N
TaskManager slots = N
Flink parallelism = N
```

如果需要更严格，可以使用 CPU quota 或 cpuset 固定 TaskManager 可用 CPU。

外部 YARN 环境建议：

```text
TaskManager vcores = N
TaskManager slots = N
Flink parallelism = N
```

但需要注意：YARN vcores 是否能形成真实 CPU 限制，取决于集群是否启用了 cgroups CPU 隔离。如果没有启用，它更像调度配额，不是强隔离。

## 9. 推荐压测口径

用于比较不同 Sink 上限时，推荐固定以下参数：

```text
CPU cores 固定
TaskManager memory 固定
TaskManager slots 固定
主并行度固定
checkpoint interval 固定
source 生成时长固定
drain 等待策略固定
每小区 CHR/PM 生成速率固定
一次只跑一个 Job
```

这样得到的 StarRocks、Iceberg、Hive、None Sink 结果才有可比性。
